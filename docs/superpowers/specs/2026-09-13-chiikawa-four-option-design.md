# Chiikawa 四选一题库重构设计

日期：2026-09-13  
状态：设计已由用户确认，待用户审阅书面规格后进入实现计划

## 背景

现有「Chiikawa 中谁和你最有缘」采用 24 题、每题 8 个选项、每个选项直接投给一个角色的 `archetype` 计分。一次完整作答需要浏览 192 段选项文案。单题信息密度过高，用户容易忘记前面的选项，或改为选择最显眼、最好笑、最喜欢的描述，而不是最符合自己的反应。

本次重构通过减少单题选项、增加题数和约束角色曝光矩阵，降低每次判断的负担，同时减少单一场景和选项位置造成的偶然偏差。它提高的是娱乐测试的结果稳定度与区分度，不把测试描述为专业或科学测评。

## 目标

- 将题库改为 32 题、每题恰好 4 个短选项。
- 将完整作答的选项浏览量由 192 段降为 128 段，下降约三分之一。
- 让八个角色获得相等的被选择机会，并尽量平衡角色两两同题比较的次数。
- 保留现有静态答题流程、报告结构和 `archetype` 票数分布展示。
- 在总票数平局时使用末 8 道综合校准题二次判定，减少固定角色顺序带来的默认胜出。

## 非目标

- 不将娱乐测试宣传为心理测量、诊断或专业评价。
- 不引入动态出题、自适应分支、角色淘汰赛或新的答题页面。
- 不建立多维特质权重模型，不凭主观权重制造“更科学”的表象。
- 不改八个结果报告的结构、COS 资产协议、记录结构或其他测试的默认计分行为。
- 不在本任务中重构整个测试引擎或调整全局最少题数基准。

## 方案选择

### 采用：四选一的平衡角色投票

每个答案继续只投给一个角色。每题展示四个角色对应的具体行为，但不在选项中出现角色名。32 题完成后，累计票数最高的角色成为结果。

选择该方案的原因：

- 与当前 `archetype` 引擎和报告分布天然兼容。
- 用户只需在四个具体反应中快速做直觉选择。
- 规则可解释、可测试，题库热更格式也不需要另建体系。
- 在没有真实样本做参数校准前，简单而平衡的投票比主观多维权重更可信。

### 未采用：多维特质加权

每个答案同时为勇气、活力、可靠、机灵等特质加分，再把特质映射到角色。它可能产生更细的分数，但必须主观定义角色模型和权重；没有样本校准时，不保证比直接投票更稳定，并会扩大引擎、报告解释和内容维护范围。

### 未采用：动态复测

先筛出候选角色，再动态生成末段对决题。它能减少平局，但要求答题页和草稿结构支持动态题目，复杂度与风险明显高于本次内容重构。

## 题库结构

### 题量和选项

- 总题数固定为 32。
- 每题固定为 4 个选项。
- 选项使用“具体场景下的直接反应”，避免抽象自评和明显褒贬。
- 每个选项尽量在一至两行内读完；编辑建议为 12—32 个中文字符，自动契约只锁定不超过 42 个 Unicode 字符，给自然表达保留空间。
- 同题四个选项不得重复，不出现角色名，也不得有一个明显比其他选项更善良、成熟或正确。

### 场景覆盖

32 题分为八类，每类四题：

1. 日常选择
2. 突发状况
3. 社交互动
4. 亲密关系
5. 冲突处理
6. 团队协作
7. 情绪表达
8. 休息与生活偏好

每个角色应在不同类别中以多种行为体现，不能只靠一个固定标签反复改写。末 8 题为综合校准题，跨多个场景检验角色差异；它们不是重复询问前题，也不向用户标记为“加权题”。

### 角色曝光矩阵

八个角色共占 32 × 4 = 128 个选项位，矩阵必须满足：

- 每个角色恰好出现 16 次。
- 每个角色在 A、B、C、D 四个选项位置各出现 4 次，降低位置偏差。
- 任意两个角色同题出现的次数尽量均衡；实现契约要求所有角色对的共现次数最大值与最小值之差不超过 1。
- 末 8 题中每个角色恰好出现 4 次，保证平票校准窗口本身不偏向某个角色。
- 相邻题不得使用完全相同的四角色组合，避免用户察觉模板轮换。

32 道四选题共有 192 次角色对共现，而八个角色共有 28 种角色对，因此无法让每一对次数完全相等；“最大差不超过 1”是可验证的近似平衡目标。

## 计分与平票规则

### 主计分

沿用 `archetype`：每个答案的 `reportId` 为对应角色加 1 票。报告页继续收到八个角色的完整票数分布，包括 0 票角色。

### 可选平票配置

在 `archetype` 计分配置中增加可选平票策略，概念接口为：

```ts
tieBreak?: {
  type: 'recent-answers'
  window: number
}
```

仅 Chiikawa 配置 `{ type: 'recent-answers', window: 8 }`。其他测试不配置该字段，继续维持“按 `scoring.reports` 定义顺序取先”的现有行为。

### 判定顺序

1. 统计全部 32 题的角色票数。
2. 若只有一个最高票角色，直接返回该角色。
3. 若多个角色并列最高，只在这些并列候选中统计末 8 题所得票数。
4. 若末 8 题产生唯一最高者，返回该角色。
5. 若仍平局，才按 `scoring.reports` 的定义顺序确定性兜底。

平票策略只决定 `reportId`，不修改完整题目的 `archetypeVotes`；报告图仍展示用户真实选择的总票数。

## 架构与数据流

- `domain/tests/chiikawaBondTest.ts` 保存静态兜底题库、角色报告和 Chiikawa 的平票配置。
- `domain/testEngine.ts` 负责纯函数计分与可选平票策略，不访问 React、HTTP、存储或平台 API。
- `pages/test-play` 继续按现有规则渲染 3 个以上选项的纵向卡片，无需加入 Chiikawa 条件分支。
- `pages/test-report` 继续消费 `reportId` 与 `archetypeVotes`，无需改变数据契约。
- 草稿内容签名包含题目和计分配置；题库变化后，旧的未完成草稿会按现有机制失效，避免答案下标错配。
- 已完成的历史记录保存最终结果，不因题库升级被重算。

## 文案更新

- 介绍文案从“24 道”改为“32 道”。
- `meta.minutes` 保持约 6 分钟：题数增加，但总选项浏览量减少，预计完成时长不会上升。
- 娱乐性质声明保持不变。
- 八个角色报告内容与结果标题保持不变，本次只调整题目和选项。

## 异常与兼容性

- `window` 必须是正整数；大于题数时按全部题目处理，避免切片越界。
- 平票窗口中的选项仍需通过现有 `reportId` 合法性校验。
- 不认识的平票策略视为无效测试定义，不静默改变结果。
- COS 动态题库若不包含 `tieBreak`，行为与当前版本完全一致。
- 旧记录没有新增配置字段，读取和报告展示不受影响。

## 测试与验收

### 聚焦自动测试

新增 Chiikawa 题库契约测试，至少覆盖：

- 恰好 32 题，每题恰好 4 个选项。
- 每个角色总曝光 16 次，且四个选项位置各 4 次。
- 任意角色对共现次数的最大值与最小值之差不超过 1。
- 末 8 题每个角色曝光 4 次。
- 题干和同题选项无重复，选项不超过 42 个 Unicode 字符。
- 32 题通过不同合法答案组合能够命中全部八个报告。
- `meta.minutes` 与 32 题匹配，介绍文案不再出现 24 题。

扩充引擎聚焦测试，至少覆盖：

- 无平局时仍由全局最高票获胜。
- 总票平局时，末 8 题在并列候选中产生胜者。
- 末 8 题仍平局时按报告定义顺序兜底。
- 未配置 `tieBreak` 的存量 `archetype` 测试行为不变。
- `archetypeVotes` 始终保存全部题目的原始总票数。

### 回归验证

- 先运行 Chiikawa 题库与 `testEngine` 的单文件 Vitest。
- 再运行完整 `npm run test`。
- 清理小程序构建缓存并重新执行微信小程序构建。
- 在微信开发者工具用 freshly built `miniapp/dist` 预览：完整作答、返回修改答案、进度显示、四选项换行、平票结果、报告分布及历史记录回看。

### 人工内容验收

人工抽查全部 32 题，确认：

- 四个答案都像真实的人会选择的反应，而不是四段角色介绍。
- 不靠角色口头禅、名字或明显梗词泄露选项归属。
- 同一个角色跨场景保持核心气质，但文案不机械重复。
- 题目没有双重否定、诱导性正确答案或专业诊断暗示。

## 成功标准

- 用户每题只面对四个清晰可选的行为，完整选项阅读量较旧版减少约三分之一。
- 八个角色具有相等曝光与位置机会，角色对比较近似平衡。
- 平票不再首先由固定角色顺序决定，而是先由末段综合题校准。
- 其他测试、报告分布、历史记录和页面交互没有行为回归。
